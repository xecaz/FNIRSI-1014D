00The one irreversible thing

Read this before you plug anything in.

Stop — unrecoverable

Your scope's per-unit calibration and configuration lives at flash offset 0x1FD000. It is written at the factory against your analog front end. There is no download for it and no way to regenerate it at home.

This was verified, not assumed: two genuine 4 MiB dumps from different scopes are byte-identical across the entire chip except two 4 KiB pages, both inside that region. Somebody else's dump is not a spare copy of yours.

Everything else on the chip is recoverable, because everything else is the same on every unit. So the whole procedure below reduces to one rule: get a verified full-chip backup before the first write, and the worst case stops being a brick and starts being an inconvenience.

01What's on the chip

Four Allwinner eGON blocks near the start, calibration near the end, and a surprising amount of nothing in between.

OffsetSizeMagicContentsChecksum field
0x0000000x3400eGON.BT0SPL — loads the splash, starts the app0xD9BA570B valid
0x0060000xBA00eGON.EXE1st executable — FEL helper0x00000000
0x0130000xE600eGON.BMPBoot splash — the target0x03098A00, not a sum
0x0270000xBC400eGON.EXE2nd executable — main scope app0x00000000
0x1FD000~0x1F4—Per-unit calibration / config—

On checksums

The eGON.BT0 field is a real, standard sunxi checksum — sum of 32-bit words with the field itself replaced by the stamp 0x5F0A6C39 — and it verifies correctly against genuine dumps. But the two .EXE blocks store 0x00000000, and a known-working patched image published upstream carries a stale BT0 checksum. So the boot ROM is not enforcing it on the SPI path.

The splash block's field, 0x776F9CC9, matches no sum over any range I tried, and is byte-identical across every dump and every patched image. Treat it as a constant and leave it alone — which is what the tool does by default.

Extracting the splash to PNG and re-encoding it back into the image reproduces the original 4 MiB file byte for byte. That round trip is what proves the format above is right rather than merely plausible.

03What you need

  • A microSD card — any size; only the first few KiB get used.
  • sunxi-fel built with SPI flash support. The stock package build often lacks it. A prebuilt copy ships in the upstream repo under Binaries/Hacked files/sunxi_stuff/.
  • fel-sdboot.sunxi, from the same directory.
  • A USB cable to the scope, and fnirsi_splash.py from this project.

You do not need to open the scope, and you do not need a SOIC clip. FEL mode reaches the SPI flash over USB.

04The procedure

Ordered by risk: everything that protects you happens before anything that changes the scope.

Step 1 — Get into FEL mode

Write the FEL boot stub to the SD card, put it in the scope, power on. The stub hands control straight to USB recovery.

Check the device node first — this writes to a raw disk
# confirm which node is your SD card, and that it is NOT your system disk
$ lsblk -o NAME,SIZE,TRAN,MODEL

$ sudo dd if=fel-sdboot.sunxi of=/dev/sdX bs=1024 seek=8 conv=fsync

# insert the card, power the scope on, then confirm it enumerated:
$ lsusb | grep 1f3a:efe8
Bus 001 Device 026: ID 1f3a:efe8 Onda (unverified) V972 tablet in flashing mode
Check twice

/dev/sdX is a placeholder. Writing this to the wrong node destroys the partition table of whatever it hits. Confirm the size and model match your SD card before pressing enter.

Step 2 — Back up the whole chip, twice

Two independent reads compared against each other. If they differ, the read is unreliable and you must not proceed — a corrupt backup is worse than no backup, because you will trust it.

Do not skip the compare
$ sudo ./sunxi-fel spiflash-read 0 0x200000 backup-1.bin
$ sudo ./sunxi-fel spiflash-read 0 0x200000 backup-2.bin

$ cmp backup-1.bin backup-2.bin && echo "reads agree"
$ sha256sum backup-1.bin | tee backup.sha256

# pull the calibration region out on its own, and put it somewhere safe
$ dd if=backup-1.bin of=calibration-0x1FD000.bin bs=4096 skip=509 count=2

Copy backup-1.bin off this machine — another drive, another host, anywhere that is not the laptop you are about to run flashing commands on.

Step 3 — Confirm your scope's actual geometry

This is the step that makes the rest safe on a 1014D rather than a 1013D.

Read your own dump, don't assume mine
$ python3 fnirsi_splash.py info backup-1.bin
$ python3 fnirsi_splash.py extract backup-1.bin -o stock.png -s 2

Look at stock.png. If it is your scope's real boot logo and info reports a sane width and height, the layout holds on your unit and you can continue. If the magic is missing or the image is garbage, stop and re-examine — do not write.

Step 4 — Make the new splash

Author at exactly the size info reported. The tool will resize and letterbox anything else onto black, but you get a sharper result by matching it yourself. Bear in mind the destination is 16-bit colour: flat brand colours and clean type survive well, subtle gradients band unless dithered, which the tool does by default.

Build the patched image — never in place
$ python3 fnirsi_splash.py replace backup-1.bin mylogo.png -o patched.bin

checksum field left at 0x776F9CC9 (unchanged)
wrote patched.bin
changed 4K pages: 15 -> ['0x13000', ... , '0x21000']
calibration region at 0x1FD000: untouched

# read it back out of the patched file and look before you commit it
$ python3 fnirsi_splash.py extract patched.bin -o preview.png -s 2

The tool refuses to emit a file whose calibration region differs from the source, so a successful write here is itself a check. Confirm the changed-page list contains only pages in 0x13000–0x21000.

Step 5 — Write it

The only destructive command in this guide
$ sudo ./sunxi-fel -p spiflash-write 0 patched.bin

# verify the chip now matches what you intended, before power-cycling
$ sudo ./sunxi-fel spiflash-read 0 0x200000 verify.bin
$ cmp verify.bin patched.bin && echo "flash matches"

Then remove the SD card and power-cycle. You should get your own logo where FNIRSI's used to be, followed by a completely normal boot into the scope application.

06If it goes wrong

Blank screen, but FEL still works

This is the ordinary failure and it is not serious. The SPL or splash block is unhappy; the boot ROM still answers over USB. Put the FEL card back in, power on, and restore:

Full restore from backup
$ sudo ./sunxi-fel -p spiflash-write 0 backup-1.bin
$ sudo ./sunxi-fel spiflash-read 0 0x200000 check.bin
$ cmp check.bin backup-1.bin && echo "restored"

Nothing enumerates at all

The F1C100s boot ROM enters FEL when it cannot find valid boot media, and the SD card is checked before SPI flash — which is exactly why the FEL card is your way back in. If USB is silent even with the card inserted, suspect the cable, the port, or power before suspecting the flash.

Scope boots but is out of calibration

If measurements are visibly wrong after a write, restore backup-1.bin in full. If you no longer have it, this is the outcome the whole guide exists to prevent, and there is no clean fix — the values were specific to your hardware.

07The other route, and what it actually does

The scope exposes its internal storage as USB mass storage, and writing a boot image to that device at an 8 KiB offset makes the scope boot from it instead of SPI flash — reversible by zeroing a single block:

Alternative firmware from SD — not a splash edit
$ sudo umount /dev/sdX1
$ sudo dd if=fnirsi_1013d.bin of=/dev/sdX bs=1024 seek=8

# and to undo it completely:
$ sudo dd if=/dev/zero of=/dev/sdX bs=1024 seek=8 count=1
Worth being precise about

This is genuinely the lowest-risk way to run different firmware, because it never writes to SPI flash at all. But it is not a way to change the stock splash: it replaces the entire boot chain with pecostm32's open firmware, which draws its own logo from its own source. Changing that means rebuilding that project, not patching a bitmap.

If your goal is your own logo in front of the stock scope application, Section 04 is the route. If you would rather run open firmware anyway, this is the safer starting point and the splash question moves into its source tree.

08What is confirmed, and what isn't

Updated after a genuine 1014D flash dump turned up — the earlier version of this guide was written from 1013D dumps and had the chip size wrong.

Confirmed on a real 1014D

A full 1014D flash backup exists upstream, under Test code/1014D_Emulator/. Against it: the splash sits at the same 0x13000, the same 0xE600 block, and the same 298 × 98 geometry as the 1013D. Extract-then-reinsert reproduces that 2 MiB image byte for byte, so the format holds on this model, not just by inference from the 1013D.

Different from the 1013D

The 1014D uses a 2 MiB chip, not the 4 MiB part on later 1013D units, and both executable blocks are different sizes (0xBA00 and 0xBC400 against 0x7A00 and 0x193A00). The consequence for you is the read length: 0x200000, not 0x400000. It also moves calibration from the middle of the chip to the last few kilobytes.

Still open

  • Whether your unit matches this dump. One 1014D backup is one data point. Step 3 is still the gate — run info on your own dump and confirm the geometry before writing anything.
  • The A/B display variants. Official firmware ships as -A- and -B- builds for different panels, with a documented symptom of the image shifting left on the wrong one. Whether that reaches the splash block is unknown.
  • The stock update file was not obtained. Latest official appears to be v3.0 dated 2021-10-06, shipped as FSI-1014.bin on a USB stick. FNIRSI's download page builds its links in JavaScript and could not be scraped; third-party mirrors were deliberately not used. The upstream dump made this non-blocking.
  • Whether the SPL validates the splash block. Still untested. The two dumps carry different values in that header field — 0x776F9CC9 and 0x03098A00 — so it is not a shared constant, but neither is a sum over any range tried, and patched images that work in the field leave it stale.
